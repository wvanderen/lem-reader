# Custom highlight tints derive readability per theme

Issue #196 widens the five highlight slots from the closed named palette to arbitrary reader-chosen colors, with a preview of the readable result before anything is created. The decision: the reader's chosen hex is stored verbatim as a snapshot (`customColor`, strict `#rrggbb`) on the slot and on every created/applied highlight record, but the PAINTED tint is always derived — `readableHighlightTint` keeps the chosen hue and caps chroma at the same calm named-marker band the #118 fills use, then bands lightness through the SAME compliant surface→AA-boundary search (`markerLightnessPair` at AA×1.02) the derived custom themes run. Ink-on-tint ≥ 4.5:1 therefore holds by construction in every theme — the seven static palettes (pinned byte-for-byte by `STATIC_THEME_HIGHLIGHT_BASES`, mirroring app.css under the extraction-anchor discipline) and the two derived custom slots (resolved through `resolveCustomTheme`, the same palette `applyTheme` writes inline, so preview = live document). The lightness normalization is the contract, not a limitation: the issue names the rendered result a readable appearance adjusted for the active theme, the hue carries the reader's identity, and the preview shows the true result before saving. One derivation feeds every paint site — the slot editor's live preview, the reader's `<mark>` overlays (prose + code twins, via the `color-custom` modifier and a per-mark `--highlight-custom` inline style), and the review panel's stripe — so preview and render cannot drift. Historical records keep their own snapshot forever: editing or recoloring a slot never touches them, and a named-color pick deletes the snapshot key (absent stays absent, never undefined-valued, so Dexie rows, the localStorage mirror, the versioned bundle, and the manifest hash all round-trip byte-stably). Forced colors keep the existing shape-only cues — every fill collapses to the system Highlight pair exactly as the named colors do, and the number/name/tags vocabulary never depended on color. Specialty-theme wash hooks, dynamic slot↔record links, and theme customization beyond this scope stay out per the issue's boundaries.

**Amended 2026-10-31 (field-feedback round):**

- **Custom chroma lifts to 0.16.** `readableHighlightTint` no longer caps the reader's pick at the named fills' calm 0.10; custom picks cap at 0.16. The lightness banding is untouched, so ink-on-tint ≥ 4.5:1 still holds by construction (chroma barely moves WCAG contrast; the tint-sweep pin verifies). Named fills stay at 0.10 — the house palette stays calm, a custom pick is the reader's identity color and carries more of it. Reason: derived tints read "dingy" regardless of hue on dimmer displays; the derivation was preserving the hue but discarding the reader's saturation.
- **Slots remember the hex.** "A named-color pick deletes the snapshot key" now applies to highlight RECORDS only. A slot keeps its custom hex dormant while a named fill is active (`customColorActive: false` with the hex retained), and the Custom pill reactivates the remembered hex instead of re-seeding. Reason: the silent destroy-on-named-pick lost the reader's chosen color; the slot is the memory home, records stay snapshot-clean. The slot schema gains the required `customColorActive: boolean` — `true` without a hex is unrepresentable (the schema's superRefine polices it into the honest corrupt routing); a pre-#222 row migrates at every settings-entry seam (a stored hex arrives ACTIVE), and the canonical write version bumps 7 → 8 so written v8 rows round-trip byte-stably (no hydration default minting keys).
- **The five slots are THE color vocabulary everywhere a highlight's color is chosen.** The annotation panel's named-color radio picker (HighlightColorEntry) and its separate "Apply slot" row collapse into ONE row of five slot pills — action buttons ("Apply slot N: name"), no checked/current state (a record's color may match no slot), no inert Custom pill, no "Slot applied." status card (the visible color + tag change is the register). The review color dialog hosts the same entry (color + additive tags through the review seam), and the floating toolbar's generic "Highlight" button is gone — the default-slot creation is the default slot's pill, leaving five slot pills + "Highlight + note". Applying a slot still snapshots only its ACTIVE hex onto the record (a named slot's application clears any earlier snapshot); a dormant hex never paints — swatches, previews, and creation payloads all read the one `activeCustomColor` gate (the one deliberate exemption: the settings editor's Custom pill previews the remembered hex — it describes what Custom reactivates; the live preview mark paints the active source). Reason: field feedback — the panel was too tall, the always-visible custom input confused, and named picks silently destroyed the custom hex; one vocabulary, one memory home.
- **The default fill's label becomes "Neutral".** `HIGHLIGHT_COLOR_LABELS.default` reads "Neutral" in every surface that shows it (the settings slot editors' named radios, the review row's "Change color, currently …" state name). The schema id stays "default" and slot 1 keeps its shipped NAME "Default" — the label collision (a named pill and a slot sharing one word) is the thing being removed; the mark's calm unprefixed aria-label for a default-colored highlight is byte-unchanged.
