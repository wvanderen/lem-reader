  <files>src/App.tsx, tests/component/App.test.tsx</files>
  <action>
Close the router half of Gap 3 (UAT test 10). The hash router currently treats every `hashchange` as a route change, so in-page fragment anchors (`#fn-N`, `#fn-ref-N`, and the skip-link `#main`) fall through `parseHash` to the list view and unmount the article (the footnote scroll target is destroyed).

In src/App.tsx:
- KEEP `parseHash` exactly as the route parser. It already maps `#/article/<id>` to the article view and every other hash to the list — that is correct ROUTE-parsing behavior (a stale/bad `#/` deep link should still land safely on the list). Do NOT change `parseHash`'s signature or return type, and keep exporting it.
- Add the route-vs-fragment distinction in the `hashchange` handler inside the existing `useEffect`. Before calling `setView(parseHash())`, guard: read `window.location.hash`; if it is non-empty AND does not start with `#/`, return early WITHOUT calling `setView`. Only hashes beginning with `#/` are app routes; bare fragment anchors are native in-page scroll targets and must not swap the view. Add a concise comment citing Gap 3 / UAT test 10 and listing the fragment namespaces that rely on native scrolling: `#fn-N` (footnote body), `#fn-ref-N` (reference back-link target), and `#main` (the SkipLink target — this guard also fixes a latent skip-link collision).

Rationale for handling the distinction in the HANDLER rather than in `parseHash`: `parseHash` must still map an unrecognized `#/` hash to the list (so a bad deep link lands safely). The handler-level guard is what prevents fragment-only hashes from ever reaching `setView`, which is what keeps the article (and its footnote target element) mounted so the browser's native scroll succeeds. On initial mount, `useState(() => parseHash())` is UNCHANGED — a fragment-only deep link on cold load correctly resolves to the list (no article is mounted yet to preserve).

Do NOT change the deep-link behavior for `#/article/<id>` (must still open the article) or the empty-hash / non-`#/`-prefixed default (must still load the list on a true navigation). The guard short-circuits ONLY hashchange events whose hash lacks the `#/` prefix.

Then CREATE tests/component/App.test.tsx (new file) — a jsdom component test of the router's fragment-vs-route distinction. Mirror the existing component-test conventions in tests/component/FixtureList.test.tsx: hoisted `vi.mock("../../src/content/repository", ...)` factory with `listArticles` and `openArticle` as `vi.fn()`; import the component after the mock; drive via `vi.mocked(...)`. Build one stub article so `listArticles` resolves with a single item and `openArticle` resolves that article for its id and `null` otherwise. Reuse the same `CanonicalArticle` shape used in the sibling tests. Reset `window.location.hash` to `""` in a `beforeEach` (jsdom persists location across tests in the same file). Cover:

- parseHash unit assertions (import the exported `parseHash`): the `#/article/a-one` hash maps to the article view; an empty hash, a bare `#/`, and an unrecognized route hash each map to the list view.
- A behavior test proving a fragment-only hash does NOT swap the view: render `<App />` starting at `window.location.hash = "#/article/a-one"`; await the article `<h1>`; then set `window.location.hash = "#fn-1"` and dispatch a hashchange via `window.dispatchEvent(new Event("hashchange"))`; assert the article `<h1>` is STILL in the document AND the fixture-list `<h1>` ("Saved articles") is NOT. Repeat the dispatch with `window.location.hash = "#fn-ref-1"` and re-assert the article stays mounted.
- A behavior test proving a `#/article/<id>` route STILL swaps the view: start at an empty hash (list visible — assert the "Saved articles" h1), then set `window.location.hash = "#/article/a-one"` and dispatch hashchange; await the article `<h1>`.

Note: in jsdom, assigning `window.location.hash` may not synchronously fire `hashchange`, so dispatch the event explicitly as shown. `Event` (not `HashChangeEvent`) is sufficient because the handler reads `window.location.hash` directly.
