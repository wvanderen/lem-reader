# Phase 5 — UI Design Contract

> Visual and interaction contract for the Durable Highlights and Notes phase.
> Generated by gsd-ui-researcher; to be verified by gsd-ui-checker.
>
> **Extends** `01-UI-SPEC.md`, `02-UI-SPEC.md`, and `04-UI-SPEC.md` (read all
> three first). This phase reuses the calm/booklike foundation verbatim —
> spacing scale, type scale, color tokens, copywriting rules, interaction
> baselines, the slim header, the native `<dialog>` slide-over, the `.status`
> live region, the WipeConfirm confirm-the-destructive-action pattern, and the
> forced-colors/reduced-motion/`:focus-visible` gates. New surfaces (inline
> `<mark>` highlight overlay, note glyph, ambiguous/orphan marker, floating
> selection toolbar, inline note popover, annotations drawer) are specified
> here and MUST stay consistent with that foundation.

## Phase Scope

Phase 5 delivers the **local annotation layer**: readers can select supported
text and create durable highlights with optional attached notes that stay
anchored to their intended canonical passage across every view change, and see
an explicit ambiguous/orphan state instead of silent reattachment. It consumes
Phase 1's D-05 grapheme substrate + the stubbed `resolveQuoteSelector` tri-state
contract, Phase 2's `<dialog>`/`.status`/debounced-save patterns, and Phase 4's
source-offset page fragments + D4-10/D4-11 anchor machinery (navigate-back runs
it in reverse). The annotation overlay renders INTO the existing semantic
renderer (D5-15) — there is NO parallel highlight renderer (DOC-02 reading
order + D-05 offset integrity depend on reusing `BlockRenderer`/`InlineRenderer`).

**In scope (Phase 5):**
1. **Inline highlight rendering** — each highlight renders as a `<mark>` with
   `tabindex=0`, `aria-label`, and a forced-colors restyle, layered into the
   existing article blocks in BOTH modes (D5-15). Cross-fragment slicing: a
   split-block highlight renders on EACH page fragment containing part of its
   grapheme range (D5-16).
2. **A single calm highlight color + note glyph** — one `--highlight` CSS token
   (warm marker, legible variants per theme) for every highlight; note-bearing
   highlights add a distinct underline glyph, NOT a second color (D5-14).
3. **Ambiguous/orphan inline marker** — an unresolved highlight renders as a
   distinct dashed-outline inline marker + a flagged drawer entry; delete is
   always available (D5-04, ANNO-07).
4. **Floating selection toolbar** — a small transient toolbar appears near a
   valid text selection offering "Highlight" and "Highlight + note" (D5-05).
5. **Inline note popover** — activating a highlight opens a small popover with
   the note field editable; "Highlight + note" opens it with a focused empty
   textarea (D5-10). One unified surface for create/edit.
6. **Annotations drawer** — a quiet header-mounted button opens a slide-over
   drawer listing all highlights+notes for THIS article in reading order, each
   tappable to jump back to its passage. Reuses the D2-01 native `<dialog>`
> slide-over pattern (D5-09).
7. **Navigate-back** — from the drawer, tapping an entry closes the drawer,
   resolves the grapheme offset to its block, turns to the page containing it
   (paginated) or `scrollIntoView`s it (scrolling), and focuses the highlight
   (D5-11). Ambiguous/orphan entries are flagged and non-navigating.
8. **Confirm-to-delete + status announce** — delete is a two-step action with
   non-destructive default focus (mirrors WipeConfirm); create/save/delete
   announce concisely in the `.status` live region (D5-12, A11Y-08).
9. **Keyboard shortcuts** `H` (highlight selection) and `N` (highlight + note)
   as the keyboard path to the toolbar actions (A11Y-01).
10. **`user-select: none`** on the always-mounted hidden measurement
    `ArticleBody` (Plan 04-08) so a reader never accidentally selects invisible
    text in paginated mode (D5-08).
11. Persistence: populates the already-reserved Dexie `highlights`/`notes`
    stores; STATE-04 Zod validation on read/write (carried from prior phases).

**Out of scope (deferred — confirmed in 05-CONTEXT.md `<deferred>`):**
- **Dedicated annotation review panel (RECV-01)** and **explicit anchor-repair
  tool (RECV-02)** — **v2**. Phase 5 surfaces ambiguous/orphan + offers delete;
  the full review/repair surface is v2.
- **Multi-color highlight palette** — **v2** (explicitly rejected for MVP in
  favor of the single calm color — D5-14).
- **Multi-block / cross-page selections**, **highlight overlap/nesting** —
  **v2** (D5-06 single-block rule, D5-13 disjoint-ranges-only).
- **Export/import of highlights & notes (PORT-01/02)** — **v2**.
- **Heading navigator and line-focus aid (ORNT-01/02)** — **v2**.
- **Formal cold/warm repagination performance budgets (ACPT-04)** — **Phase 6**.
  Phase 5 annotation rendering must not visibly degrade repagination, but
  formal budget acceptance is Phase 6.

**Locked by STACK.md / AGENTS.md (do not revisit):**
- **Selection/Range APIs** capture ephemeral selections immediately into durable
  normalized-text selectors. **Persisting DOM `Range`, XPath-only anchors, page
  numbers, pixels, or React component paths is FORBIDDEN.**
- W3C-inspired `TextPositionSelector` + `TextQuoteSelector` over normalized
  text (the anchor pair; D5-03 persists BOTH).
- Authored CSS layers + CSS custom properties (NO Tailwind, NO component
  suite, NO shadcn). Semantic HTML as the renderer; DOM reading order equals
  document order. React 19 + TypeScript + Vite 8 SPA; React state/context only.
- Playwright across Chromium/Firefox/WebKit for layout/accessibility truth —
  highlight rendering (esp. cross-fragment slicing D5-16, forced-colors D5-15,
  selection capture D5-08, ambiguous/orphan surfacing D5-04) MUST be validated
  in real browsers across the 6-fixture corpus × theme × mode matrix, NOT in a
  DOM emulator.

**Locked by 05-CONTEXT.md decisions (D5-01 through D5-16 — do NOT re-ask):**
- Anchor encoding + resolution rules (D5-01, D5-02, D5-03, D5-04).
- Single contiguous run within ONE normalized-text block (D5-06); broad
  eligible set "if you can read it, you can highlight it" (D5-07).
- Paginated-mode selection binds to the visible page fragment via
  `data-block-index` (D5-08).
- Disjoint ranges only — reject overlapping new selections (D5-13).
- Single calm color + note glyph, `<mark>` + tabindex=0 + ARIA + forced-colors
  restyle (D5-14, D5-15). Cross-fragment render (D5-16).
- Native `<dialog>` drawer reusing D2-01 (D5-09); inline popover for note edit
  (D5-10); navigate-back closes drawer + jumps + focuses (D5-11); confirm-to-
  delete mirroring WipeConfirm (D5-12).

**Locked by Phase 1 + 2 + 4 UI-SPEC (carried forward unchanged):**
- Spacing scale (multiples of 4) and the 44px `--touch` minimum.
- Type scale: exactly 4 sizes (14 / 18 / 22 / 32px), 2 weights (400 / 600).
- Body serif / UI sans / code mono font stacks.
- Warm-paper color tokens (Sepia default + Light + Dark via `[data-theme]`) +
  accent reserved-for list + contrast contract.
- Copywriting microcopy rules (sentences not fragments; direct second person;
  never blame the reader; never leak jargon — "highlight"/"note" not "anchor"/
  "selector"/"TextQuoteSelector"/"grapheme"/"fragment").
- Interaction baselines: visible focus (2px outline + 2px offset),
  reduced-motion gate, forced-colors gate, programmatic status pattern,
  always-underlined links, the `.status` card pattern (D2-13), the slim
  persistent header (D2-02), the `<dialog>` slide-over (D2-01), the WipeConfirm
  confirm-the-destructive-action pattern (Plan 02-02), the hairline +
  SectionAnnouncer (D2-12), the page-turn controls + fallback banner (Phase 4).
- Layout breakpoints and the invariant calm reading measure.

**Resolved by this spec (discretion areas delegated by 05-CONTEXT.md):**
- Floating-toolbar positioning + lifecycle + coexistence with page-turn
  controls and swipe/zoom (D5-05 discretion). → §Interaction 25.
- Exact `--highlight` token value + note-glyph design (D5-14 discretion). →
  §Color + §Interaction 27.
- Drawer copy / lifecycle / empty-state + ordering/filtering (D5-09
  discretion). → §Copywriting + §Interaction 30.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (authored CSS layers per STACK.md; shadcn/component suites forbidden) |
| Preset | not applicable |
| Component library | none — semantic native HTML elements only (`<mark>`, `<dialog>`, `<button>`, `<textarea>`, `<header>`, `<ul>`/`<li>`, the existing `<article>`/`<main>`/`<header>`). The highlight overlay renders INTO the existing `BlockRenderer`/`InlineRenderer` output (no fork). |
| Icon library | none. The drawer-trigger glyph, the note-bearing underline cue, and the ambiguous/orphan flag are inline SVG / CSS text-decoration (no library). All icons MUST carry an accessible name via `aria-label` or visually-hidden text and MUST be `aria-hidden="true"` when decorative. |
| Font | System stacks only (no web fonts this phase). See Typography. |

**Three overlay mechanisms, three interaction contracts (researcher rationale
for mixing `<dialog>` + Popover API + a position-fixed element rather than
forcing one):**

| Surface | Mechanism | Why this mechanism |
|---------|-----------|--------------------|
| Annotations drawer (D5-09) | native `<dialog>` + `showModal()` | A true slide-over panel: backdrop + focus-trap + Esc + trigger-restore are all desired and all free. Reuses the `.settings-panel` pattern verbatim (D2-01). |
| Note popover (D5-10) | Popover API (`popover="manual"`) | A small positioned editing surface near the highlight. Needs top-layer rendering + no light-dismiss (typing must not close it) + no backdrop (the article stays visible). `<dialog>`/`showModal` is too heavy (centered + backdrop); `show()` loses the top-layer guarantee. The Popover API is a sibling browser primitive to `<dialog>` and consistent with STACK.md "browser primitives first." All target engines (current Chromium/Firefox/WebKit) ship it. |
| Floating selection toolbar (D5-05) | conditionally-rendered `position: fixed` element | A transient, non-modal 2-button affordance tied 1:1 to live selection state. `popover="auto"` would light-dismiss on the very `mouseup` that finalizes the selection; `popover="manual"` + a `<dialog>` are heavier than a toolbar needs. The Kindle/Readwise/Apple Books pattern is a positioned element whose visibility tracks the selection. `z-index` lifts it above page content; it never needs the top layer. |

All three inherit the global forced-colors + reduced-motion + `:focus-visible`
gates from `app.css`. No mechanism introduces a transition/animation property.

## Spacing Scale

Carried forward verbatim from Phase 1+2+4. All spacing MUST round to a token
here. Phase 5 adds no new tokens.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Note-glyph underline offset, drawer entry internal padding, popover excerpt-to-textarea gap |
| sm | 8px | Floating-toolbar button internal gap, drawer entry row gap, popover internal padding, ambiguous/orphan marker outline offset |
| md | 16px | Floating-toolbar button padding-inline, popover padding, drawer entry block padding, drawer section gaps |
| lg | 24px | Drawer section padding, popover outer padding, drawer header padding |
| xl | 32px | Layout gaps, drawer body outer margin on wide viewports |
| 2xl | 48px | Major section breaks (unchanged) |
| 3xl | 64px | Page-level top/bottom padding of scrolling view (unchanged) |
| touch | 44px | Minimum interactive hit area — drawer-trigger button, floating-toolbar buttons, popover Done/Delete buttons, drawer entry jump affordance, every prior-phase control |

**Exceptions (override the scale where stated):**
- **Touch target minimum: 44 × 44 px** (`--touch`) for EVERY interactive control
  added this phase (drawer-trigger, both floating-toolbar buttons, popover Done
  + Delete, the drawer entry's jump affordance which spans the whole entry).
- **Focus ring: 2px solid `--focus-ring` outline + 2px offset** (Phase 1
  baseline; applies to the `<mark>` highlight, the toolbar buttons, the popover
  controls, the drawer-trigger, and each drawer entry).
- **Header height: 48px** (unchanged — Phase 5 fits the new drawer-trigger
  inside the existing slim header's `.header-controls` group; the header does
  NOT grow).
- **Note-bearing underline glyph: 2px thick, 3px offset** (text-decoration;
  not a spacing token — see §Interaction 27).
- **Ambiguous/orphan dashed outline: 1px thick, 1px offset** (outline; not a
  spacing token — see §Interaction 28).
- **`<mark>` fill is a color token** (`--highlight`), not a spacing value.

## Typography

Phase 1+2+4's type scale and font stacks are the **defaults** and remain in
force for every surface. Phase 5 adds no new role. The floating-toolbar
buttons, the popover excerpt/label, the drawer title/entries, and the status
announces all reuse existing roles.

**Font stacks (system-only — no web fonts this phase):** unchanged from Phase 4
(Body serif/sans/dyslexia-friendly selectable; UI chrome + code fixed).

**Type scale (unchanged from Phase 1+2+4 — exactly 4 sizes, 2 weights):**

| Role | Size | Weight | Line Height | Stack |
|------|------|--------|-------------|-------|
| Body | 18px *(default; user-steppable)* | 400 (regular) | preset-driven | selected body stack |
| Meta / Label | 14px | 400 (regular) | 1.45 | UI sans |
| Subheading (h2, h3, h4) | 22px *(relative `em`)* | 600 (semibold) | 1.3 | selected body stack |
| Display (article title h1) | 32px *(relative `em`)* | 600 (semibold) | 1.2 | selected body stack |

**Phase 5 surface assignments (no new role, just role assignment):**

| Surface | Role | Notes |
|---------|------|-------|
| Floating-toolbar buttons ("Highlight" / "Highlight + note") | Meta / Label (14px UI sans, 400 weight, `--ink`) | Two quiet text buttons. NEVER accent-colored in default state — mirrors the page-turn chevron discipline. The reader's eye stays on the selected text, not the toolbar. |
| Floating-toolbar invalid-selection hint ("Select within one block…") | Meta / Label (14px UI sans, 400 weight, `--ink-soft`) | Replaces the buttons when the selection is invalid. Calm, non-alarming. |
| Note popover — excerpt (read-only context) | Meta / Label (14px UI sans, italic, `--ink-soft`) | The highlighted text shown for context, truncated to ~200 chars with an ellipsis. Italic + soft so it recedes behind the editable note. |
| Note popover — textarea label | n/a — visually-hidden `<label>` | "Note" — accessible name only (the textarea is the focus target). |
| Note popover — textarea | Body (18px / selected body stack, 400 weight) | The note is reader-authored prose; it uses the BODY role so it reads like the article, not like chrome. Line-height inherits the preset. |
| Note popover — Done / Delete buttons | Meta / Label (14px UI sans, 400 weight, `--ink`) | Quiet chrome buttons. Delete uses `--destructive` border (mirrors WipeConfirm). |
| Drawer title | Subheading (22px UI sans — *exception*, see note) | The drawer is a `<dialog>` sibling of `.settings-panel`; its title reuses the panel-title treatment (22px / 600 / UI sans). This is the SAME exception `.settings-panel-header h2` already makes (app.css L430-436). |
| Drawer entry — highlighted text excerpt | Body (18px / selected body stack, 400 weight) | The reader's own highlighted prose. Truncated to ~120 chars with ellipsis. |
| Drawer entry — note text (if present) | Meta / Label (14px UI sans, 400 weight, `--ink-soft`) | Recedes behind the excerpt so the excerpt leads visually. |
| Drawer entry — ambiguous/orphan flag | Meta / Label (14px UI sans, 600 weight, `--ink-soft`) | Short label ("Couldn't relocate" / "Ambiguous"). 600 weight distinguishes it from the note text. |
| Drawer entry — edit/delete affordances | Meta / Label (14px UI sans, 400 weight) | Quiet text buttons inside each entry. |
| Drawer empty-state heading | Subheading (22px UI sans, 600) *(drawer-title exception)* | Mirrors the drawer title treatment. |
| Drawer empty-state body | Meta / Label (14px UI sans, 400 weight, `--ink-soft`) | Calm instructional copy. |
| Status announces (create/save/delete) | n/a — live-region text only | Concise: "Highlight saved." / "Note saved." / "Highlight deleted." Mirrors the SectionAnnouncer pattern. |

> **Drawer-title exception note:** the `.settings-panel-header h2` rule in
> `app.css` (L430-436) already declares the settings-panel title as `22px /
> 1.3 / 600 / UI sans` — an intentional exception to the "Subheading = body
> serif" default because panel titles are chrome, not article content. The
> annotations drawer title + empty-state heading reuse this exact treatment
> (the drawer is a sibling `<dialog>`). This is NOT a new type role; it is the
> existing panel-title exception applied to a second panel.

**Relative-unit rule (carried from Phase 2+4):** Body and drawer-entry excerpt
sizes scale with the reader's chosen body step (the drawer excerpt uses the
body stack so a reader's typography choices apply to their own highlighted
prose). Drawer title, popover labels, toolbar buttons, and status copy are
fixed UI-sans px sizes (chrome — they do not scale with body).

**Block rhythm:** unchanged from Phase 1 inside both modes. The `<mark>`
overlay does NOT alter the block's margin/line-height — it wraps existing
inline text and inherits its line box. A highlight spanning a line break
renders continuously (the fill wraps with the text); no layout shift.

## Color

Phase 5 keeps every Phase 1+2+4 token. **One new token family is added:
`--highlight`** (the single calm warm-marker fill, per D5-14). It is its OWN
token — distinct from `--accent` and NOT part of the 60/30/10 accent split.
The highlight fill is reserved exclusively for `<mark>` elements inside the
article body; it never decorates chrome.

### New token: `--highlight` (D5-14, warm marker per theme)

A low-saturation warm marker derived from the D-07 warm-paper direction. Each
theme gets a legible variant (D2-09). Values chosen so `--ink` on `--highlight`
≥ 4.5:1 in every theme (ink stays the article text color; the marker is the
background).

| Theme | Selector | `--highlight` value | Rationale |
|-------|----------|---------------------|-----------|
| Sepia (default = `:root`) | `:root` | `#f5e6c8` | Warm pale ochre — sits between `--surface` (#fbf8f3) and a dry-marker yellow. Evokes a highlighter on cream paper. `--ink` (#1f1b16) on it: ~13:1. |
| Light | `[data-theme="light"]` | `#f7eaa6` | Warm pale yellow, slightly brighter for the brighter Light surface (#fcfcfa). `--ink` (#1a1a1a) on it: ~14:1. |
| Dark | `[data-theme="dark"]` | `#5c4a23` | Warm golden-brown, lighter + warmer than the dark surface (#1b1814) so the marker reads as a highlight. `--ink` (#ede6d9) on it: ~7.5:1. |

**Forced-colors override (D5-15, A11Y-05):** under `@media (forced-colors:
active)`, the `<mark>` MUST NOT lose meaning. It maps to the user's system
highlight colors and adds a fallback underline so the cue is not color-alone:

```css
@media (forced-colors: active) {
  mark.highlight {
    background-color: Highlight;
    color: HighlightText;
    /* Fallback cue (shape, not color): a bottom rule survives even if the
       UA forces Highlight/HighlightText to the same pair. */
    text-decoration: underline;
    text-decoration-color: CanvasText;
    text-underline-offset: 2px;
  }
}
```

The three inline highlight states (normal / note-bearing / ambiguous-orphan)
remain distinguishable under forced-colors by SHAPE, not color (see §Interaction
26–28): solid fill vs. dotted underline vs. dashed outline.

### Theme tokens (unchanged — Sepia default + Light + Dark via `[data-theme]`)

Sepia = Phase 1 `:root` defaults. Light + Dark overrides via `[data-theme="..."]`
on `<html>` (Phase 2 D2-09). All token values verbatim from `02-UI-SPEC.md
§Color`; reprinted in `src/app.css`. **The only addition:** the `--highlight`
token declared in `:root` and overridden under each `[data-theme]` selector
(above), following the exact pattern `--surface`/`--accent`/etc. already use.

### Role usage (60/30/10 + highlight)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--surface` | App background, article-view background, paginated page background, header background (unchanged) |
| Secondary (30%) | `--surface-raised` | Settings panel surface, annotations drawer surface, resume / storage / pagination-fallback banner surface, wipe-confirmation surface, **note popover surface**, **floating-toolbar surface**, code blocks, figures (extended) |
| Accent (10%) | `--accent` | See reserved-for list below |
| Destructive | `--destructive` | "Reset local data" destructive action border (Phase 2) + **highlight Delete button border** (Phase 5 — mirrors WipeConfirm; the consequence is conveyed beyond copy for forced-colors safety). The Delete action is the ONLY new destructive surface. |
| Highlight (content overlay) | `--highlight` | **`<mark>` fill inside the article body ONLY.** Never on chrome, never on drawer entries, never on the toolbar. The drawer represents highlights as text excerpts (no fill); the live highlight fill lives only on the inline `<mark>`. |

**Accent reserved for (explicit list — never "all interactive elements"):**
1. Hyperlinks inside the article body.
2. The original-source URL link in the provenance block.
3. The "Open article" CTA on each fixture-list row (Phase 1).
4. The collapsed-state marker on each unsupported-content disclosure (Phase 1).
5. `:focus-visible` outline on every focusable element — **including the
   `<mark>` highlight, the toolbar buttons, the popover controls, the
   drawer-trigger, and each drawer entry** (Phase 5 additions inherit the
   baseline).
6. The progress-hairline fill (Phase 2 D2-12).
7. The gear icon when the panel is open (Phase 2).
8. The selected-state indicator on the active theme / preset / size / measure
   option (Phase 2).
9. The mode-toggle glyph when `aria-pressed="true"` (Phase 4).
10. The page-turn chevron on hover and on `:focus-visible` (Phase 4).
11. **Phase 5 additions (minimal):**
    - The **drawer-trigger glyph when `[aria-expanded="true"]`** (drawer open —
      mirrors the gear-button open/closed rule exactly; closed state uses
      `--ink-soft`).
    - The **floating-toolbar buttons on hover and on `:focus-visible`** (matches
      the page-turn chevron hover discipline; default state is `--ink` so the
      toolbar reads as quiet chrome, not an accent call-to-action).
    - The **drawer entry's jump affordance on hover and on `:focus-visible`**
      (the entry is a button; hover/focus signals "this will navigate").

Accent MUST NOT be used for: body text, headings, chrome backgrounds, dividers,
captions, panel section headings, banner body copy, the `<mark>` highlight fill
(use `--highlight`), the closed-state drawer-trigger, the default-state toolbar
buttons, the drawer-entry excerpts/notes, or the ambiguous/orphan marker (use
`--ink-soft` dashed outline).

### Contrast contract (checker validates, every theme — extended from Phase 2+4)

- `--ink` on `--surface`: ≥ 4.5:1 (body text). *(unchanged)*
- `--ink` on `--surface-raised`: ≥ 4.5:1. *(unchanged)*
- `--ink` on `--highlight`: ≥ 4.5:1 (**NEW** — the article text inside a
  highlight MUST stay legible; this is the core legibility contract for D5-14).
  Validated values above (~13:1 Sepia, ~14:1 Light, ~7.5:1 Dark).
- `--ink-soft` on `--surface`: ≥ 4.5:1. *(unchanged)*
- `--ink-soft` on `--surface-raised`: ≥ 4.5:1 (**NEW** — toolbar hints, drawer
  notes, popover excerpts sit on `--surface-raised` and use `--ink-soft`).
- `--accent` on `--surface` and on `--surface-raised`: ≥ 4.5:1 (links count as
  body text). *(unchanged)*
- `--focus-ring` against any surface it appears on: ≥ 3:1 (WCAG 2.2 SC 1.4.11).
  *(unchanged; applies to the `<mark>` focus ring too)*
- `--destructive` text/border on its surface: ≥ 3:1 (UI component threshold;
  the Delete button border conveys consequence — mirrors WipeConfirm).
- Forced-colors mode (`@media (forced-colors: active)`, already global in
  `app.css`) MUST NOT remove: link underlines, focus outlines, the disclosure
  marker, the selected-option indicator, the gear's open/closed distinction,
  the mode-toggle's pressed/unpressed distinction, the page-turn chevrons'
  enabled/disabled distinction, **the `<mark>` highlight cue** (conveyed by the
  system Highlight/HighlightText pair AND a fallback underline — §Interaction
  26), **the note-bearing distinction** (dotted underline — §Interaction 27),
  **or the ambiguous/orphan distinction** (dashed outline — §Interaction 28).
  All three inline states survive forced-colors by SHAPE, not color alone.

## Copywriting Contract

Phase 1+2+4's copywriting and microcopy rules carry forward unchanged
(sentences, not fragments; direct second person; never blame the reader; never
leak internal jargon — no "anchor," "selector," "TextQuoteSelector,"
"TextPositionSelector," "grapheme," "fragment," "block," "revision,"
"compound key," "Dexie," "IndexedDB," or "schema" in user-facing copy; dates
via `Intl.DateTimeFormat`). The reader-facing words are **"highlight"** and
**"note"** — never "annotation," "marker" (except in CSS class names), or
"selector." The new Phase 5 surfaces:

| Element | Copy |
|---------|------|
| Header — drawer-trigger button (`aria-label`, no highlights yet) | `Highlights and notes` — icon-only; `aria-expanded` reflects open/closed. No visible text label. The visible glyph is a quiet highlighter/bookmark inline SVG (`--ink-soft` closed, `--accent` open). |
| Header — drawer-trigger button (`aria-label`, N highlights exist) | `Highlights and notes, {N}` where {N} is the count via `Intl.NumberFormat`. The count also appears as a small superscript badge on the glyph (visually-hidden duplicate avoided — the count is in the label). |
| Header — drawer-trigger SR announce on open (polite) | *(none — opening a drawer is a deliberate reader action, not a consequential event. The drawer title is announced by the `<dialog>` accessible name.)* |
| Drawer — title | **Highlights and notes** (panel heading; the `<dialog>`'s accessible name via `aria-labelledby`) |
| Drawer — close | `aria-label="Close highlights and notes"`; visible × glyph (mirrors settings-panel close) |
| Drawer — empty-state heading (article has no highlights) | **No highlights yet** |
| Drawer — empty-state body | Select any text in the article to highlight it. You can add a note to any highlight, and come back here to find them. |
| Drawer — entry, jump affordance (`aria-label`) | `Go to highlight: {excerpt}` — the whole entry is a button; activating it runs D5-11 navigate-back. `{excerpt}` is the first ~60 chars of the highlighted text. |
| Drawer — entry, jump affordance (visible text) | The highlighted text excerpt (truncated ~120 chars, ellipsis). No separate "Jump" button label — the excerpt IS the affordance (the whole row is a button). |
| Drawer — entry, note text (if present) | The note text verbatim (truncated ~200 chars, ellipsis). Italic + `--ink-soft` so it recedes behind the excerpt. |
| Drawer — entry, ambiguous flag | **Couldn't find a unique match** (short label, `--ink-soft`, 600 weight) |

## Interaction Patterns

Phase 1+2+4's interaction baselines (visible focus, reduced-motion,
forced-colors, programmatic status, always-underlined links, disclosure,
skip link, settings panel, location restore, scroll-save, progress hairline,
storage failure, persistent header, mode toggle, page-turn controls,
pagination fallback) carry forward unchanged and apply to every new control.
Phase 5 adds:

### 24. Highlight creation — selection scope + capture (D5-05, D5-06, D5-07, D5-08, ANNO-01)

- **Selection mechanism:** native text selection — mouse drag, touch drag, or
  Shift+arrows. The reader selects text the way they always select text; there
  is no "highlight mode" to enter.
- **Capture:** on `selectionchange` (debounced via `requestAnimationFrame` so
  rapid selection shaping doesn't thrash), the listener checks the current
  `window.getSelection()`. If non-collapsed AND entirely within a single
  eligible block's text node tree AND within the visible reading surface
  (scrolling `.article-body` OR the visible `.page-fragment` — NOT the hidden
  `.article-body-measurement`, which is `user-select: none` per D5-08), the
  selection is VALID and the floating toolbar appears (§25). Otherwise the
  toolbar shows the relevant invalid-selection hint or stays hidden.
- **Eligible blocks (D5-07 — "if you can read it, you can highlight it"):**
  paragraph, heading, blockquote children, list-item children, figure
  CAPTION, code-block source, footnote-reference marker. Inline marks
  (link/code/strong/em per D-04) inside a prose selection ride along inside
  the grapheme range — a link stays active inside a highlight (D5-07).
- **Single-block rule (D5-06):** a selection spanning more than one
  normalized-text block, or crossing a page boundary in paginated mode, is
  INVALID. The toolbar shows "Select within a single block to highlight it."
  Multi-block / cross-page selections are explicitly **v2**.
- **Disjoint-ranges rule (D5-13):** a valid selection whose grapheme range
  intersects ANY persisted highlight's range is INVALID. The toolbar shows
  "This overlaps an existing highlight." Overlap/nesting is **v2**.
- **Paginated-mode binding (D5-08):** the selection must be inside the VISIBLE
  `PageFragmentView` (queried via `data-block-index` → `article.blocks` →
  `normalizeText` offset). The always-mounted hidden measurement `ArticleBody`
  (Plan 04-08) gets `user-select: none` so a reader never accidentally selects
  invisible text. The single-block rule means highlights always fit on the
  current page; turning away and back re-renders persisted highlights on
  whatever page they land on (§26).
- **Capture-to-anchor:** on `Highlight` / `Highlight + note` activation (or
  the `H` / `N` shortcut), the ephemeral DOM `Range` is converted IMMEDIATELY
  to a durable `TextPositionSelector` + `TextQuoteSelector` pair (via
  `deriveQuoteSelector()` — already shipped in `normalizeText.ts`). The DOM
  `Range` is NEVER persisted (STACK.md forbids it). The selection is then
  cleared and the `<mark>` renders from the persisted anchor.

### 25. Floating selection toolbar — positioning + lifecycle (D5-05 discretion, A11Y-01/04/06/07)

> D5-05 locks "floating toolbar on selection" + the two actions ("Highlight"
> / "Highlight + note") + the mental model (Kindle/Readwise/Apple Books).
> WHERE it appears, HOW it dismisses, and how it coexists with the page-turn
> controls + swipe/zoom are settled here.

- **Mechanism:** a conditionally-rendered `position: fixed` element (NOT a
  popover, NOT a `<dialog>` — see §Design System rationale). `z-index: 8`
  (above page content at `z-index: 1` and the hairline/chevrons at `z-index:
  5`; below the header at `z-index: 10` and below dialogs/popovers in the top
  layer). It never needs the top layer — it is a transient affordance, not a
  modal surface.
- **Position (ABOVE the selection, edge-clamped):**
  - Computed from `selection.getRangeAt(0).getBoundingClientRect()` on each
    `selectionchange` (rAF-throttled). The toolbar is horizontally centered on
    the selection's midpoint, vertically placed `--space-sm` (8px) ABOVE the
    selection's top edge.
  - **Edge-avoidance (horizontal):** clamp the toolbar's computed `left` so it
    never overflows the viewport. If `centerX - toolbarWidth/2 < --space-sm`,
    pin to `left: var(--space-sm)`. If `centerX + toolbarWidth/2 >
    viewportWidth - --space-sm`, pin to `right: var(--space-sm)`.
  - **Flip-below (vertical):** if the selection is within ~60px of the top of
    the viewport (i.e. not enough room above for the toolbar + its `--space-sm`
    gap), the toolbar flips to BELOW the selection (`--space-sm` below the
    selection's bottom edge). This covers the case where the reader selected
    text right under the header.
  - **Paginated mode:** the same logic runs against the visible page fragment's
    rect. The toolbar clamps to the page content-box width (not the full
    viewport) so it never overlaps the page-turn chevrons at the viewport
    edges. The chevrons sit outside the content-box by design (04-UI-SPEC
    §Layout); the toolbar sits inside it. No overlap.
- **Lifecycle (appear):** on a VALID non-collapsed selection (§24), the toolbar
  appears at the computed position. It does NOT auto-focus (the reader's
  focus/selection stays where it is — auto-focusing the toolbar would steal
  the selection). The toolbar buttons are in the tab order AFTER the current
  selection's containing element.
- **Lifecycle (dismiss):** the toolbar dismisses on ANY of:
  1. The selection collapses or becomes invalid (cleared, or moved to a
     different/invalid range).
  2. `Escape` is pressed while the toolbar is visible.
  3. Either action button is activated (the highlight is created; the toolbar's
     job is done).
  4. The reader turns the page, switches modes, navigates away, or opens the
     drawer/settings panel (the selection context is gone).
  5. The note popover opens (the toolbar dismisses; the popover takes over).
- **Coexistence with swipe/zoom (A11Y-04, D4-06):** the toolbar listens to
  `selectionchange` (a DOM event), NOT to touch events. Pinch-zoom
  (multi-touch) never creates a text selection, so it never fires the toolbar.
  A horizontal swipe that doesn't change the selection never fires it. If a
  touch-drag creates a native text selection (the browser's own text-selection
  gesture), `selectionchange` fires and the toolbar appears — the touch path
  is the same as the mouse path. The toolbar's own hit area uses
  `touch-action: manipulation` (no double-tap zoom delay on the buttons).
- **Keyboard path (A11Y-01 — the toolbar is a pointer/touch affordance; the
  keyboard path is the H/N shortcuts, §33):** after a Shift+arrows selection,
  the reader presses `H` (highlight) or `N` (highlight + note). The toolbar is
  still VISIBLE during keyboard selection (so a sighted keyboard reader sees
  the affordance), but the shortcuts are the primary keyboard path — the
  reader is not forced to Tab to the toolbar. (Tab still reaches the toolbar
  buttons in DOM order as a fallback.)
- **Geometry:** `--surface-raised` background, `--hairline` border, 4px radius,
  `--space-sm` internal gap between the two buttons. Each button: `min-height:
  var(--touch); padding-inline: var(--space-md); font: 400 14px/1 UI sans;
  color: var(--ink)`. Hover/`:focus-visible`: `color: var(--accent)` (matches
  the page-turn chevron hover discipline). **No shadow** — `--surface-raised` +
  the `z-index` lift + the `--hairline` border are sufficient (mirrors the
  no-shadow discipline of every prior chrome surface).
- **Reduced motion (A11Y-06):** the toolbar appears/disappears as an instant
  mount/unmount. No transition/animation property on any toolbar selector.
- **Reflow (A11Y-04):** at 320 CSS px and 200% zoom, the toolbar clamps within
  the viewport with both buttons visible. If the two buttons + their `--space-sm`
  gap exceed the viewport width minus `2 * --space-sm`, the toolbar stacks the
  buttons vertically (column flex) so both stay reachable. The invalid-
  selection hint is a single line and truncates gracefully.

### 26. Inline highlight rendering — `<mark>` + ARIA + forced-colors (D5-15, D5-16, A11Y-02/03/05)

- **Element:** each highlight renders as `<mark class="highlight"
  id="hl-{highlightId}" tabindex="0"
  aria-label="Highlight{ with note}: {excerpt}"
  aria-haspopup="dialog">…inline text…</mark>`. The `<mark>` wraps the
  highlighted grapheme range INSIDE the existing block/inline renderer output
  — it does NOT fork `BlockRenderer`/`InlineRenderer` (DOC-02 reading order +
  D-05 offset integrity depend on reusing the same semantic output).
- **Fill:** `background-color: var(--highlight)`. The article text color
  (`--ink`) is inherited — the marker is the background, not the text. Links
  inside a highlight keep their `--accent` color + underline (D5-07).
- **Focusable + popovertarget:** `tabindex="0"` makes each highlight a stop in
  the article's tab order (A11Y-02). Activating it (Enter/Space/click) opens
  the inline note popover (§29). `:focus-visible` draws the standard 2px
  `--focus-ring` outline + 2px offset (Phase 1 baseline).
- **Reading order (A11Y-03):** the `<mark>` is inline in the article DOM. In
  paginated mode, only the current page's marks are in the tab/reading order
  (the same single-content-tree rule Phase 4 enforces). No duplicate active
  content tree.
- **Cross-fragment slicing (D5-16):** in paginated mode, a single-block
  highlight whose block is split across a page boundary (D4-01) renders on
  EACH page fragment containing part of its grapheme range. Each fragment gets
  its own `<mark>` for the visible slice, all sharing the same `highlightId`
  (via a `data-highlight-id` attribute). Both marks are focusable; opening the
  popover from either shows the same note + delete. **No silent gaps at a page
  turn** — the reader sees the passage as one continuous thing the pagination
  merely sliced for display.
- **Reduced motion (A11Y-06):** the `<mark>` fill is instant (a background
  color, not a transition). No animation on highlight creation/removal — the
  `<mark>` mounts/unmounts as an instant state change.
- **Forced-colors (A11Y-05):** see §Color — the `<mark>` maps to system
  `Highlight`/`HighlightText` + a fallback underline so the cue survives even
  if the UA collapses the pair.

### 27. Note-bearing highlight glyph (D5-14 discretion — dotted underline)

> D5-14 locks "single calm color + note glyph (underline variant or margin
> dot), NOT a second color." The exact glyph design is settled here.

- **Glyph = dotted underline.** A note-bearing `<mark>` (one whose persisted
  `NoteRecord` has non-empty text) adds:
  ```css
  mark.highlight.has-note {
    text-decoration: underline dotted;
    text-decoration-color: var(--ink-soft);
    text-decoration-thickness: 2px;
    text-underline-offset: 3px;
  }
  ```
- **Why dotted underline (not a margin dot, not an inline icon):**
  - **Pure CSS** (no extra DOM node) — survives forced-colors as a SHAPE (the
    dots render even when colors are overridden), and renders correctly on
    cross-fragment slices (D5-16: each fragment's `<mark>` gets its own
    underline; a margin dot would only show on one fragment).
  - **Booklike** — evokes a marginalia cue, the calm "this passage has a note"
    signal a reader recognizes from print.
  - **Distinct from link underlines** — links use a SOLID `--accent` underline
    (global `a` rule); note-bearing highlights use a DOTTED `--ink-soft`
    underline. The two cues are visually distinct by STYLE (solid vs dotted)
    and COLOR (accent vs ink-soft). The rare case of a link inside a note-
    bearing highlight shows both cues layered — readable because they differ
    on two axes.
  - **Doesn't consume horizontal space** — works inside tight paginated
    content-boxes where a margin glyph would clip.
- **The bare-highlight vs note-bearing distinction is NEVER color-alone**
  (A11Y-05): the `<mark>` fill is the same `--highlight` for both; the
  dotted underline is the differentiator. Under forced-colors, the system
  Highlight/HighlightText pair applies to both, and the dotted underline
  remains as the shape cue.
- **The glyph is `aria-hidden` decorative** — the note presence is conveyed
  to AT via the `<mark>` `aria-label` ("Highlight with note: …") and the
  popover's editable textarea, not by the underline itself.

### 28. Ambiguous/orphan inline marker (D5-04, ANNO-07)

- **Distinct from a normal highlight.** An unresolved highlight (D5-02:
  `resolveQuoteSelector` returns `"ambiguous"` or `"orphan"`) does NOT render
  with the `--highlight` fill. It renders as:
  ```css
  mark.highlight.unresolved {
    background-color: transparent;
    color: var(--ink);
    outline: 1px dashed var(--ink-soft);
    outline-offset: 1px;
  }
  ```
- **Why dashed outline (not a fill, not a second color):**
  - **Shape-distinct from the normal highlight** (solid fill vs dashed
    outline) — the reader can tell at a glance "this highlight has a problem"
    without reading the aria-label.
  - **Shape-distinct from the note-bearing glyph** (dotted underline vs
    dashed outline) — three inline states (normal / note-bearing /
    ambiguous-orphan) are distinguishable by SHAPE alone, surviving forced-
    colors.
  - **No fill** — an unresolved highlight's exact position is uncertain (it's
    anchored to the stored position HINT for orphans, or the first candidate
    for ambiguous); a fill would overstate confidence. The outline marks the
    vicinity without claiming the range is exact.
- **Position:** for an ORPHAN, the marker appears at the stored
  `TextPositionSelector` hint (the last-known position). For an AMBIGUOUS, it
  appears at the first candidate match. Both are "best-effort vicinity"
  renderings; the aria-label + drawer flag convey the uncertainty.
- **Still focusable + activatable:** `tabindex="0"`, same `aria-haspopup`
  pattern. Activating an unresolved marker opens the popover showing the
  stored excerpt (read-only context) + the ambiguous/orphan copy + Delete.
  Edit-note is disabled for unresolved highlights (there's no confident range
  to attach the note to). The reader can still delete (D5-04: "delete is
  always available").
- **Drawer flag (D5-04):** the same highlight appears as a flagged entry in
  the drawer (§30) with the "Couldn't find a unique match" / "Couldn't
  relocate this highlight" copy. Tapping an unresolved drawer entry does NOT
  navigate (§31) — the entry shows the flag + the excerpt + delete only.

### 29. Inline note popover — positioned editing surface (D5-10, ANNO-02/03)

- **Mechanism:** Popover API — `<div popover="manual" id="highlight-popover"
  class="highlight-popover" role="dialog" aria-label="Highlight note">`.
  `popover="manual"` (not `auto`) so typing doesn't light-dismiss it.
  `showPopover()` / `hidePopover()` controlled by React state.
- **Why Popover API (see §Design System rationale):** top-layer rendering
  without a backdrop, positions near the highlight, no light-dismiss in manual
  mode. The existing `<dialog>`/showModal pattern is reserved for true modals
  (settings panel, wipe-confirm, annotations drawer) where backdrop +
  focus-trap + centering are desired.
- **Trigger:** activating a `<mark>` (Enter/Space/click/tap) calls
  `showPopover()`. The popover anchors near the highlight (computed from the
  `<mark>`'s `getBoundingClientRect()`, edge-clamped like the toolbar). If
  `data-highlight-id` indicates a note-bearing highlight, the textarea shows
  the persisted note text; if bare, the textarea is empty with the placeholder.
- **On "Highlight + note" creation (D5-10):** the toolbar's "Highlight + note"
  button (or the `N` shortcut) creates the highlight AND immediately opens the
  popover with a FOCUSED EMPTY textarea. This is the one unified create/edit
  surface: "Highlight" creates bare; "Highlight + note" creates + opens the
  editor.
- **Contents:**
  1. Visually-hidden `<label>` "Highlighted text:" + a read-only excerpt
     (italic, `--ink-soft`, truncated ~200 chars) — orients the reader (and AT)
     to what the note is attached to.
  2. Visually-hidden `<label for>` "Note" + `<textarea>` (Body role, the
     reader's chosen body stack). Autosizes to content up to a max height
     (~6 lines), then scrolls.
  3. Actions row: **Done** (closes the popover) + **Delete** (starts the
     two-step confirm, §32).
- **Persistence (D2-03 pattern):** the textarea persists DEBOUNCED (mirrors
  the settings-panel live-apply + debounced-save — there is no Save button).
  The debounce window is the planner's call (~800ms-1s, matching the settings
  cadence). On `Done` / `Escape`, a final flush fires before close so no edit
  is lost. An empty textarea = no note (the highlight stays bare; the dotted-
  underline glyph is removed).
- **Focus management:**
  - On open via "Highlight + note": focus → textarea (empty, ready to type).
  - On open via activating an existing highlight: focus → textarea (with
    existing text selected, so the reader can edit or replace).
  - On `Done` / `Escape` / outside-click (manual mode ignores outside-click,
    so only Done/Escape close): focus → back to the `<mark>` (predictable
    focus restoration — A11Y-02, mirrors the gear-button restore pattern).
  - The popover is a small surface; Tab cycles excerpt → textarea → Done →
    Delete and wraps. It does NOT need a heavy focus-trap (the Popover API
    keeps it in the top layer; background content is not inert, but the
    reader's attention is on the popover). Shift+Tab from the textarea wraps
    to Delete; Tab from Delete wraps to the excerpt label.
- **Reduced motion (A11Y-06):** the popover appears/disappears as an instant
  show/hide (the Popover API's own transition is disabled by the global
  `prefers-reduced-motion` gate). No fade.
- **Reflow (A11Y-04):** at 320 CSS px, the popover fills the viewport width
  minus `2 * --space-md` insets. The textarea + buttons stack vertically if
  needed; both action buttons keep their 44px hit area.
- **Coexistence with the drawer/settings panel:** if the reader opens the
  drawer or settings panel while the popover is open, the popover closes
  first (the drawer/settings are higher-priority surfaces; the popover's edit
  is flushed before close).

### 30. Annotations drawer — header slide-over + ordering/filtering (D5-09 discretion, ANNO-03/04)

> D5-09 locks "inline popover on the highlight + a header-mounted list drawer
> reusing the D2-01 native `<dialog>` pattern." The drawer copy, lifecycle,
> empty-state, and ordering/filtering are settled here.

- **Drawer-trigger button (D5-09):** a quiet icon button in the existing slim
  header's `.header-controls` group, placed **inline-start of the mode-toggle**
  (so the group reads `[annotations] [mode] [gear]` = `[content] [view]
  [settings]` — grouped by scope). It appears ONLY when an article is mounted
  (hidden on the fixture list, where there are no highlights). It mirrors the
  gear-button geometry exactly: 44×44 hit area, transparent background,
  `--ink-soft` default, `--accent` ONLY when `[aria-expanded="true"]` (drawer
  open). `aria-haspopup="dialog"`. A small count badge (superscript, `--ink-
  soft`) shows the highlight count when >0; it's `aria-hidden` (the count is
  in the `aria-label`).
- **Drawer = native `<dialog>` slide-over (reuses `.settings-panel`):** the
  drawer is a `<dialog class="annotations-drawer">` shown via `showModal()`,
  sliding over from the inline end (right in LTR) — the EXACT geometry of the
  settings panel (near-full-width sheet <640px; ~400px column ≥640px; `::backdrop`
  covers the article; free focus-trap + Esc + trigger-restore + inert
  backdrop). The CSS class differs (`.annotations-drawer`) so the panel's
  internal layout can differ, but the sheet geometry + the focus/Esc/backdrop
  behavior are identical.
- **On open:** focus → drawer title (or first entry if non-empty). The
  trigger's `aria-expanded` → `true`. The trigger button gets `--accent` (mirrors
  gear-open).
- **On close (Esc, scrim click, or ×):** focus → back to the drawer-trigger
  button (predictable focus restoration — A11Y-02). `aria-expanded` → `false`.
- **Drawer contents:**
  1. **Header row:** title "Highlights and notes" + × close button (mirrors
     settings-panel header).
  2. **Body:** an ordered list (`<ol>`, reading order) of entries, OR the
     empty-state card.
- **Ordering (LOCKED by D5-09 — reading order is the canonical default):**
  entries are ordered by grapheme START offset ascending = canonical document
  order = the order the reader encounters them reading top-to-bottom. This is
  the single MVP view.
- **Filtering/sorting (researcher call — NONE for MVP):** no sort/filter
  affordances in the MVP drawer. Rationale:
  - The calm/booklike aesthetic favors a single predictable order over
    controls that compete with content (READ-04).
  - Reading order is the most useful single order for "find that thing I
    highlighted" — it maps to the reader's spatial memory of the article.
  - Sort/filter (by date, by note-bearing-only, by unresolved-only) is the v2
    RECV-01 review panel's job. MVP keeps the drawer to one calm ordered list.
  - The drawer DOES visually flag ambiguous/orphan entries (D5-04) so a reader
    scanning the list can spot them without a filter — the flag is the
    progressive-enhancement cue.
- **Entry layout (each entry = one `<li>` containing one button + meta):**
  - The whole entry is a `<button class="drawer-entry" type="button">` (the
    jump affordance spans the entire entry — A11Y-07 large hit area).
  - Inside: the highlighted-text excerpt (Body role, truncated ~120 chars,
    ellipsis) leads; the note text (Meta/Label, italic, `--ink-soft`, truncated
    ~200 chars) follows if present; the ambiguous/orphan flag + body appears
    instead of the note if unresolved.
  - A small actions row (Edit note / Delete) sits inline-end — these are
    secondary `<button>`s inside the `<li>` but OUTSIDE the jump button (so
    they don't trigger the jump). They are quiet text buttons, Meta/Label size.
  - **Ambiguous/orphan entries (D5-04):** the jump button is `disabled` (the
    entry can't navigate — §31); a visually-hidden note in the `aria-label`
    explains why. Edit is disabled (no confident range); Delete stays enabled.
- **Empty state (article has no highlights):** the drawer body shows a single
  calm card (reuses `.status` geometry — `--surface-raised` + `--hairline`
  border + 4px radius + `--space-lg` padding): heading "No highlights yet" +
  body "Select any text in the article to highlight it. You can add a note to
  any highlight, and come back here to find them." The copy teaches the
  feature without alarming the reader.
- **Drawer lifecycle on article open:** if ≥1 highlight is unresolved (D5-04)
  on article open, a one-time polite announce fires: "{N} highlight(s)
  couldn't be relocated." This directs the reader to the drawer without
  forcing it open (the drawer stays closed until the reader opens it — we
  don't interrupt reading). The drawer-trigger's count badge reflects the
  total (resolved + unresolved).
- **Reduced motion (A11Y-06):** the drawer slides/appears as an instant
  show/hide (the global gate disables the slide). No fade.
- **Reflow (A11Y-04):** the drawer inherits the settings-panel reflow contract
  verbatim (near-full-width sheet <640px; ~400px ≥640px). Each entry fills the
  drawer width; the actions row wraps below the excerpt on narrow widths.

### 31. Navigate-back — drawer entry → passage (D5-11, ANNO-04)

- **On a resolved entry tap:** the drawer closes; the highlight's grapheme
  offset is resolved to its block via `data-block-index` (the D4-10/D4-11
  anchor machinery in reverse — `src/pagination/anchor.ts`); then:
  - **Paginated mode:** turn to the page containing that block (the same
    `commitTurn` path the chevrons use — Plan 04-09), then focus the `<mark>`.
  - **Scrolling mode:** `scrollIntoView({ block: "center" })` the block
    (reusing Phase 2's `findScrollTarget` exactly — do not fork), then focus
    the `<mark>`.
  - **Focus (D4-07 pattern):** focus moves to the `<mark>` itself (the reader
    navigated TO this highlight; they expect to land on it). The `<mark>`'s
    `:focus-visible` outline confirms the destination. If the reader then
    activates it, the popover opens (§29).
- **On an ambiguous/orphan entry tap:** NOTHING navigates. The entry's jump
  button is `disabled` (§30); tapping it is a no-op (the reader sees the flag
  + the excerpt + delete in the drawer already). This honors ANNO-07's
  "explicit state instead of silent reattachment" — we never jump to an
  uncertain location.
- **Silent + instant (A11Y-06):** the navigate-back is silent (no announce —
  the reader deliberately chose to navigate; the `.status` region is reserved
  for unsolicited consequential events per D3-04). The page-turn or scroll is
  instant under reduced-motion; otherwise a single calm `scrollIntoView` is
  acceptable in scrolling mode (the global gate disables it when the reader
  prefers reduced motion). Paginated mode never animates the turn.
- **Mode-switch not required:** navigate-back works in whichever mode the
  reader is currently in. If the reader is in paginated mode and the target
  is on page 7, the reader lands on page 7. We do NOT force a mode switch.

### 32. Delete confirm + status announce (D5-12, ANNO-03, A11Y-08, STATE-03)

- **Two-step delete (mirrors WipeConfirm, Plan 02-02, Pitfall 8):**
  - **Step 1:** the reader activates **Delete** in the popover (or in the
    drawer entry's actions). The popover body replaces with the confirm
    prompt: "Delete this highlight?" + the excerpt shown for orientation + two
    buttons (**Delete** destructive / **Keep** cancel). In the drawer, the
    entry's actions row replaces with the same two buttons inline.
  - **Step 2 (confirm):** the reader activates **Delete** (destructive). The
    highlight + its note are removed together (`notes.highlightId` cascade).
    The popover closes (or the drawer entry unmounts). The `<mark>` unmounts
    from the article. A polite announce fires: "Highlight deleted."
  - **Step 2 (cancel):** the reader activates **Keep**. The popover/drawer
    returns to its prior state. Nothing is deleted. No announce.
- **Non-destructive default focus (Pitfall 8):** on step 1, focus moves to the
  **Keep** button (the non-destructive action) — an accidental Enter cannot
  delete. This mirrors WipeConfirm's `[data-initial-focus]` on the cancel
  button (Plan 02-02 decision in STATE.md).
- **Destructive-button styling:** the confirm-step **Delete** button uses
  `--destructive` border + `--destructive` text color (mirrors `.wipe-confirm-
  destructive` geometry exactly — forced-colors safety so the consequence is
  conveyed beyond the label). Hover inverts (fill `--destructive`, text
  `--surface`). The **Keep** button uses the neutral `--hairline` border
  (mirrors `.wipe-confirm-cancel`).
- **Status announces (D5-12, A11Y-08, D3-04 — `.status` reserved for
  consequential events):**
  - **"Highlight saved."** — fires on `Highlight` / `Highlight + note`
    activation (after the anchor is captured + persisted).
  - **"Note saved."** — fires ONCE after the debounce window commits a note
    edit (not on every keystroke — the announce is itself debounced so rapid
    typing doesn't chatter). If the reader types and closes before the window,
    the `Done` flush fires the announce.
  - **"Highlight deleted."** — fires on confirm-step Delete (step 2).
  - **"{N} highlight(s) couldn't be relocated."** — fires once on article open
    if ≥1 unresolved highlight exists (§30).
  - These announces use the existing `.status` live region (D2-13/D3-04). They
    are concise, non-repetitive, and never blame the reader.
- **No announce for:** opening/closing the drawer (deliberate reader action),
  opening/closing the popover (deliberate), navigate-back (deliberate), or
  routine repagination re-rendering highlights (silent — D3-04 reserves the
  region for consequential events).

### 33. Keyboard shortcuts — H / N (A11Y-01, extends Phase 4's keyboard bundle)

- **`H`** — highlight the current selection (equivalent to tapping the
  toolbar's "Highlight" button). Creates a bare highlight; the toolbar
  dismisses; "Highlight saved." announces.
- **`N`** — highlight the current selection AND open the note popover with a
  focused empty textarea (equivalent to tapping "Highlight + note"). Creates
  the highlight + opens the editor in one action.
- **Registration:** registered globally on `window` when an article is
  mounted. Removed when the article unmounts. The listener uses
  `{ passive: true }` and calls `preventDefault()` ONLY when it actually
  handles the key (never on H/N inside an input, the textarea, a dialog, or
  the settings panel — the handler checks `event.target` and bails on form
  fields/`[contenteditable]`/dialog descendants).
- **Guard:** the handler checks `window.getSelection()`. If the selection is
  collapsed or invalid (§24), H/N do nothing (no fallback action — H/N are
  selection-dependent). This avoids hijacking H/N when the reader is just
  reading.
- **Coexistence with the `M` shortcut (Phase 4):** M switches reading mode;
  H/N act on the selection. The three shortcuts don't conflict (different
  keys, different scopes). The keyboard-help paragraph (Phase 4) is EXTENDED
  with the H/N line (§Copywriting).
- **Reduced motion (A11Y-06):** H/N trigger instant highlight creation + (for
  N) instant popover show. No animation.

### 34. Selection-invalid hints + overlap rejection (D5-06, D5-13, ANNO-01)

- **The floating toolbar shows HINTS instead of actions when the selection is
  invalid** (§25 lifecycle). Two hint states:
  - **Multi-block / cross-page (D5-06):** "Select within a single block to
    highlight it." The hint replaces the two action buttons at the toolbar's
    computed position. Dismisses when the selection changes to valid or
    collapses.
  - **Overlap (D5-13):** "This overlaps an existing highlight." Same geometry.
    Dismisses when the selection changes.
- **Hints are non-blocking:** they don't trap focus, don't open a dialog,
  don't prevent the reader from adjusting the selection. They are calm,
  non-alarming plain-language cues (never "Error," "Invalid," or "Disallowed").
- **Hints respect the same edge-avoidance + flip-below logic** as the action
  toolbar (§25).
- **Keyboard path for invalid selections:** H/N on an invalid selection do
  nothing (§33 guard). The reader adjusts the selection with Shift+arrows
  until valid; the toolbar updates in real time.

## Layout

Phase 1+2+4's visual hierarchy and breakpoints carry forward. Phase 5 adds
the drawer-trigger's header slot, the floating-toolbar geometry, the note
popover geometry, and the `<mark>` overlay's interaction with the page
content-box.

**Header stacking (top of viewport — unchanged except the new trigger):**
1. `header.app-header` — 48px, sticky/fixed top, full width. Wordmark +
   `.header-controls` group `[annotations-trigger?] [mode-toggle] [gear]`.
   The annotations-trigger appears only when an article is mounted. The
   header does NOT grow — the three-control group + wordmark fit the same
   48px row (the gear/mode-toggle/annotations-trigger share the same 44×44
   geometry; the `.header-controls` gap is `--space-sm`).
2. `div.progress-hairline` — 2px, unchanged.
3. `<main id="main">` — unchanged inset.

**Inline `<mark>` overlay geometry:**
- The `<mark>` is an inline element wrapping existing text. It does NOT alter
  the block's line-height, margin, or width — the fill wraps with the text
  across line breaks (the reader sees a continuous highlight, not per-line
  boxes). No layout shift on highlight creation/removal.
- The dotted underline (note-bearing) + dashed outline (unresolved) are
  text-decoration/outline — they also don't alter layout.
- In paginated mode, a cross-fragment highlight (D5-16) renders one `<mark>`
  per visible fragment slice. The slices are computed from the fragment's
  source-offset range vs. the highlight's grapheme range (deterministic — the
  D4-01/D4-02 fragment model already carries per-fragment grapheme ranges).

**Floating selection toolbar geometry:**
- `position: fixed`; coordinates computed from the selection's
  `getBoundingClientRect()` (rAF-throttled on `selectionchange`).
- `--surface-raised` background, `--hairline` border, 4px radius, no shadow.
- Two buttons side-by-side (`flex-direction: row; gap: var(--space-sm)`); each
  `min-height: var(--touch); padding-inline: var(--space-md)`.
- Edge-clamp: horizontal pin to `--space-sm` from viewport edge; vertical
  flip-below when <60px above. In paginated mode, clamp to the page
  content-box width (not full viewport) to avoid the page-turn chevrons.
- `z-index: 8` (above content + hairline/chevrons at 5; below header at 10
  and below dialogs/popovers in the top layer).
- Stacks vertically (`flex-direction: column`) at <320px-equivalent if both
  buttons + gap don't fit.

**Note popover geometry:**
- Popover API (`popover="manual"`) — renders in the top layer (no `z-index`
  needed; above everything including the header).
- `--surface-raised` background, `--hairline` border, 8px radius, no shadow.
- `max-width: 380px`; `width: calc(100vw - 2 * var(--space-md))` on narrow
  viewports. Positioned near the `<mark>` via `getBoundingClientRect()`,
  edge-clamped, with a flip-below fallback (same logic as the toolbar).
- Internal: `padding: var(--space-lg)`; `display: flex; flex-direction: column;
  gap: var(--space-md)`. Excerpt → textarea → actions row.
- Textarea autosizes to content (max ~6 lines); actions row uses
  `flex-wrap: wrap; justify-content: flex-end; gap: var(--space-sm)`.

**Annotations drawer geometry:**
- Reuses `.settings-panel` sheet geometry verbatim (native `<dialog>`,
  `showModal`, `::backdrop`, near-full-width <640px, ~400px ≥640px).
- Internal: header row (title + ×) + body (`<ol class="drawer-list">` or
  empty-state card).
- Drawer entries: each `<li>` fills the drawer width; `padding: var(--space-md)`;
  `border-bottom: 1px solid var(--hairline)` between entries (calm list
  rhythm). The jump button is `display: block; width: 100%; text-align: start`.
  Excerpt leads; note/flag follows; actions row sits inline-end (or wraps
  below on narrow widths).

**Reflow (A11Y-04):** at 320 CSS px equivalent and 200% browser zoom:
- The header MUST keep the wordmark, annotations-trigger, mode-toggle, and
  gear visible in one row. If the wordmark must yield, it truncates first
  (controls are operation-critical). If the row still overflows, the
  annotations-trigger glyph stays (it's article-content-critical); the
  wordmark truncates to "Lem" or hides entirely as a last resort.
- The floating toolbar clamps within the viewport; buttons stack vertically
  if needed.
- The note popover fills the viewport width minus `2 * --space-md`; textarea +
  buttons stack.
- The annotations drawer is a near-full-width sheet (same as settings panel).
- The `<mark>` overlays, dotted underlines, and dashed outlines render
  correctly under zoom/reflow — they're inline text-decoration/outline, which
  scale with the text.
- All keyboard, pointer, touch, and selection interactions MUST remain
  operable (A11Y-01, A11Y-07).

| Breakpoint | Behavior |
|-----------|----------|
| `< 640px` | Single column everywhere. Header full width with truncating wordmark; toolbar clamps + stacks vertically if needed; note popover near-full-width; drawer = near-full-width sheet. `<mark>` overlays inline. |
| `640–1024px` | Article body capped at the reader's chosen measure. Toolbar clamps to content-box. Note popover ~380px near the highlight. Drawer ~400px column over scrim. |
| `≥ 1024px` | Same measure cap — the reading column does NOT widen with viewport (calm measure is invariant). More margin room for the toolbar/popover edge-clamp. Fixture list (Phase 1) max three columns. |

**Reduced-motion (A11Y-06, critical):** Phase 5 ships **zero required
animations.** The `<mark>` fill is instant (a background color). The toolbar
appears/disappears as instant mount/unmount. The popover shows/hides via the
Popover API (its own transition disabled by the global gate). The drawer
slides/appears as instant show/hide (the global gate disables the slide).
Navigate-back's `scrollIntoView` is governed by the global `scroll-behavior`
gate (instant under reduced motion; a single calm scroll otherwise in
scrolling mode; never animated in paginated mode). Phase 5 introduces no
transition/animation property on any new selector (the toolbar/popover/drawer
state changes are mount/unmount + color, not motion). The reader with
reduced-motion preference gets the same instant, calm experience as every
other reader.

## Registry Safety

| Registry | Blocks Used | Safety Gate |
|----------|-------------|-------------|

Phase 5 uses zero third-party UI blocks. All new UI is native HTML (`<mark>`,
`<dialog>`, Popover API) + authored CSS + inline SVG. The shadcn gate is **not
run** because the project stack explicitly forbids Tailwind, component suites,
and shadcn (STACK.md "What NOT to Use"; AGENTS.md). This is a locked decision,

target engines (current Chromium/Firefox/WebKit per Phase 6's acceptance
matrix). No vetting gate applies.
