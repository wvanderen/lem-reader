<objective>
PAGE-09 banner detaches before reader can act (4 failures on firefox + webkit).

ROOT CAUSE: The auto-dismiss lifecycle (registered by ArticleView L460-472 on first scroll/pointer activity) tears the banner down BEFORE the reader's "Switch to pages" / × click lands. The Playwright trace shows "element was detached from the DOM, retrying" → 30s timeout. Chromium passes by timing luck.

The lifecycle listener uses `{ passive: true, once: true }` on `pointerdown`. When the reader moves the pointer to click the banner, the `pointerdown` event fires on the banner (or its wrapper), the listener dismisses the banner, the subsequent `click` event finds the element detached. This is the race.

Purpose: Restore PAGE-09 — the banner must stay mounted + clickable long enough for the reader to read the reason + act on it.
Output: Auto-dismiss lifecycle that does NOT race the click path; UI-SPEC copy preserved byte-for-byte.
</objective>

  <action>
    The root cause: the `pointerdown` listener at ArticleView L463-466 fires DURING the banner click. The pointer enters the banner → pointerdown → listener fires → setShowFallbackBanner(false) → React unmounts the banner → the subsequent click event has no target. The Playwright trace shows "element was detached from the DOM, retrying" → 30s timeout.

    The ResumeBanner has the same pattern (L437-450) but does not have this problem because the ResumeBanner's actions (Resume/Start-from-top) are not inside the banner's pointerdown dismissal path the same way — the user clicks a specific button which Playwright can target by role without ambiguity. The PaginationFallbackBanner's "Switch to pages" button + × button ARE the click targets the auto-dismiss interferes with.

    Acceptable fixes (pick the cleanest — the executor confirms by running the failing e2e in firefox with --headed):

    FIX A (preferred — tightest scope): the `pointerdown` listener should IGNORE pointerdown events that originate INSIDE the banner. The auto-dismiss is for "the reader started scrolling / interacting elsewhere" — not for "the reader is interacting with the banner itself." Concretely:
    - In the dismiss handler, check `event.target instanceof Node && bannerEl?.contains(event.target)` — if the pointerdown is inside the banner, do NOT dismiss.
    - The banner element is queryable via `document.querySelector(".pagination-fallback-banner")` at dismiss time, OR thread a ref from ArticleView to the banner wrapper.

    FIX B (alternative): drop the `pointerdown` auto-dismiss; keep ONLY the `scroll` auto-dismiss. The banner is a non-blocking `.status` card; scrolling is a clear signal the reader has moved on. Pointer activity on the banner itself is the reader acting on it — that should NOT dismiss. Pointer activity OUTSIDE the banner + outside any control is ambiguous — err on keeping the banner visible (the × dismiss is always available). This is simpler but changes the UI-SPEC §Interaction 23 contract slightly ("auto-dismisses on first scroll OR pointer activity" → "auto-dismisses on first scroll"). The copy + the explicit × / Switch to pages actions stay.

    FIX C (alternative): delay the auto-dismiss. Instead of `{ once: true }` immediate dismissal, use a short timer (e.g. 500ms after the FIRST pointer activity) so the click-action sequence completes first. This is fragile (timing-dependent) — prefer Fix A.

    Choose FIX A unless the executor finds the bannerEl.contains check is unreliable (e.g. if the banner unmounts during the click for a different reason). Document the choice in the SUMMARY.

    REGARDLESS of fix: preserve the verbatim UI-SPEC §Copywriting banner copy. The heading, body, announce, switch button label, and dismiss aria-label MUST NOT change. Re-read src/reader/PaginationFallbackBanner.tsx and confirm the copy matches UI-SPEC lines 351-355 byte-for-byte. If any copy drifted during a prior plan, restore it.

    Preserve the T-04-15 contract: the banner's "Switch to pages" action calls onSwitchToPages which routes through handleToggleMode which clears sessionModeOverride WITHOUT calling update({readingMode}). Verify by reading ArticleView.handleToggleMode (L182-209): when sessionModeOverride !== null, it clears the override and does NOT persist. The fallback path never calls update({readingMode}). The T-04-15 e2e (line 137) must stay green.
