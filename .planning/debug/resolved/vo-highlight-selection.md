# Debug Session: H highlight shortcut is dead under VoiceOver

## Symptoms

- **Expected behavior:** A VoiceOver user selects text using VO's text-selection model (VO+Enter to start selection, arrow keys to extend, VO+Enter to end) and presses H to create a highlight — the highlight is created and announced (ANNO-01, UI-SPEC §Interaction 33). Equivalently, the mouse-driven selection-toolbar "Highlight" button should work for any user who can produce a browser text selection.
- **Actual behavior:** H does nothing under VoiceOver. The shortcut silently bails because `window.getSelection()` is collapsed — VO's text selection does not surface to the browser Selection API as a recognized Range. The reported observation: "H doesn't work for highlighting text."
- **Errors:** None. Silent failure — the handler returns early (no preventDefault, no action) per its selection-dependent design.
- **Timeline:** Found in the Phase 6 ACPT-02 acceptance run (2026-08-09). The H/N shortcuts were built in Phase 5 Plan 05-02 (ANNO-01) and are SELECTION-DEPENDENT BY DESIGN — they intentionally bail when `window.getSelection()` is collapsed so H/N are not hijacked while just reading (UI-SPEC §33 guard).
- **Reproduction:** Safari + VoiceOver, open any article, use VO commands to select a text range, press H. Nothing happens. (Mouse-drag-select then H works, because that produces a real Selection API range.)

## Current Focus

- hypothesis: **(REVISED 2026-08-10)** The original "VO selection substrate gap" hypothesis is ELIMINATED by tester evidence (the tester created a highlight via the toolbar path using VO+Enter/arrows selection — see Evidence). The NEW leading hypothesis is a **VoiceOver single-key Quick Nav key conflict**: when macOS VoiceOver's single-key Quick Nav (toggled VO-Q, a SEPARATE feature from arrow-key Quick Nav VO-Shift-Q) is ON, bare single letters navigate instead of reaching the app. H is VoiceOver's "next heading" quick-nav key, so pressing H is intercepted by VoiceOver at the OS/accessibility layer BEFORE the browser dispatches the window `keydown` the app listens on (`src/routes/ArticleView.tsx:497`). The app handler never fires → H appears dead, while the toolbar path (Tab → Enter, not a bare letter) works fine. This also generalizes: bare single-letter shortcuts are fragile across ALL major SRs (NVDA and JAWS reserve h=next-heading in browse/virtual-buffer mode by default), so H is a latent landmine for SR users generally — not VO-specific.

## Eliminated

- **(ELIMINATED 2026-08-10) VoiceOver selection substrate gap.** Original hypothesis: VO's text-selection model (VO+Enter / arrow extend) does not produce a Range that `window.getSelection()` recognizes, so the selection-dependent H/N handlers bail at `ArticleView.tsx:425-429` and the toolbar never renders. **Disproved by tester evidence:** the tester created a highlight under VO via the toolbar path, which requires `window.getSelection()` to be non-collapsed AND `captureSelection` to succeed. The selection substrate is fine. The failure is H-specific and upstream of the Selection API (a key-handling conflict, not a selection-data gap). The "block-level highlight affordance" design change (original next_action branch B) is therefore NOT needed.
- **(REJECTED 2026-08-10) Runtime VO detection + key remap.** Considered: detect VoiceOver and remap H only for SR sessions. Rejected because VoiceOver exposes no reliable, stable app-visible signal (no standard `navigator`/UA flag, no `prefers-*` media query, no event). Heuristic detection would be brittle and would not cover NVDA/JAWS. The robust answer is a path that works regardless of SR state (the toolbar) rather than branchy SR detection.

## Resolution

- root_cause: macOS VoiceOver **single-key Quick Nav** (VO-Q), NVDA browse mode, and the JAWS virtual buffer all **reserve the bare letter `H` = "next heading"** and consume it at the OS/accessibility layer BEFORE the browser dispatches the `window` `keydown` the app listens on (`src/routes/ArticleView.tsx:497`). The app's `onKey` handler therefore never fires for bare `H`, so H appears dead under SR while the selection-toolbar path (Tab → Enter / VO+Space — no bare quick-nav letter) works fine. This is a **documented platform constraint, not an app defect**: the tester's VO text-selection (VO+Enter/arrows) DOES surface to `window.getSelection()` (a highlight was created via the toolbar), eliminating the earlier "VO selection substrate gap" hypothesis. Bare single-letter shortcuts are simply the wrong primitive for an SR-critical action across all three major SRs. No app-side mitigation can make bare `H` fire while the SR toggle is on.
- fix: **Option A — docs reframe (minimum-change, no source-logic change to H/N/M wiring).** Promoted the selection-toolbar (a `role="toolbar"` with two real native `<button>`s — "Highlight" ≡ H and "Highlight + note" ≡ N — Tab-reachable, Enter/VO+Space-activatable, tester-confirmed working under VO) to the **documented PRIMARY screen-reader path** for creating highlights. Bare `H`/`N` remain as **sighted keyboard/mouse conveniences** (their contract for non-SR users is unchanged — the keydown wiring, `captureSelection`, `SelectionToolbar`, and `NotePopover` were NOT touched). (1) `docs/ACCEPTANCE-PROTOCOL.md` Flow C rewritten so the primary SR path is VO-select → toolbar appears → Tab to "Highlight" → Enter (VO+Space); added a preamble blockquote noting SRs reserve single-letter keys (VO-Q H=next heading; NVDA/JAWS likewise) so bare H is sighted-only, and a trailing blockquote demoting H/N to keyboard/mouse conveniences; expected outcomes kept as role + accessible name per Pitfall 7. (2) `src/routes/ArticleView.tsx` visually-hidden keyboard-help `<p>` reframed so it no longer promises H as an SR path — it now directs SR users to Tab to the "Highlight" toolbar button + Enter and explains SRs reserve single-letter keys. Option B (add a SR-safe modifier combo) was NOT taken — macOS makes clean combos awkward (Cmd+H = hide app; Alt+H = dead key; Ctrl+H = browser history).
- verification: (1) **TypeScript clean** (`tsc --noEmit` exit 0). (2) **No test asserts the changed keyboard-help text** — the only `grep` hit for the old phrasing is a file-header comment in `keyboard-shortcuts.spec.ts:2`, not an assertion. (3) **Annotation e2e suite: 153 passed, 6 failed — the 6 failures are EXACTLY the pre-existing ones attributed to `bf6dd88` or earlier** (`capture-highlight.spec.ts:121` "technical-post: code-block source is capturable" × chromium/firefox/webkit, and `forced-colors-shapes.spec.ts:82` "bare vs note-bearing vs unresolved shape distinction" × chromium/firefox/webkit). **ZERO new failures** introduced by this docs + help-text change. Notably `keyboard-shortcuts.spec.ts` — including the "Toolbar buttons are keyboard-focusable (fallback keyboard path, UI-SPEC §25)" case — passed across all 3 engines, confirming the toolbar SR path the docs now promote is verified by automation. (4) **Docs greps confirm**: Flow C now states "Primary SR path = the selection toolbar (Tab → Enter)" and "sighted keyboard/mouse convenience only"; the old C3 "(or H — the highlight shortcut)" phrasing is removed; the keyboard-help `<p>` now reads "Screen-reader users: after selecting text, Tab to the 'Highlight' toolbar button and press Enter." (5) Final VO confirmation of the reworded help text remains a human checkpoint (investigator cannot run VoiceOver) — but no code path changed, so the ACPT-02 run state is unaffected by this change.
